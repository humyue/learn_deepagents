# 0001 — 学习目标定为「理解 harness 原理」，而非「做出应用」

- **日期**：2026-10-08（会话 1）
- **状态**：已确认

## 背景

用户提出想学 Deep Agents，给出官方文档概览页，并要求把左侧导航的全部章节"总结成一个新的教学网站"。

在开课前通过结构化提问确认了四件事：动机、语言、覆盖范围、动手环境。

## 决定

1. **动机 = 深入理解 agent harness 原理**（而非"做实际项目"或"评估选型"）。
2. **语言 = 中文讲解 + 英文术语原文**。
3. **范围 = 一次性覆盖官方导航全部页面**，共 35 个页面。
4. **环境 = 暂无 LLM API Key**，所以练习形式是代码阅读 / 机制推演 / 离线自测，不布置必须运行的任务。

## 理由

- 若动机是"做项目"，课程应当以 quickstart 为骨架、以能跑通为达标线；但用户的兴趣在**机制**，
  因此课程骨架改为「四层执行环境 + 四层上下文 + 委派层 + 管控层」这套 harness 解剖结构，
  quickstart 只作为解剖对象出现一次。
- 没有 API Key ⇒ 不能依赖"跑一遍就懂了"这种反馈回路。必须把反馈回路转移到
  **检索式自测**（recall）与**代码逐行判读**上，这也恰好更利于 storage strength。

## 后果（Consequences）

- 课程会出现"机制深度"和"覆盖面"的张力：35 个页面里只有约三分之一与原理强相关。
  应对方式：引入 Tier A / Tier B 分层，Tier A 深挖，Tier B 精炼但完整，保证零遗漏。
- 站点必须能离线浏览（`file://` 直接打开），所以放弃 mermaid 等需要网络的渲染，
  改用纯 CSS 流程图。
- 一旦用户拿到 API Key，本记录需要修订：Tier A 章节要从"读"升级为"练"。

## 待验证

- "先讲机制、后讲 API"对用户是否真的更有效？在 3–5 课之后回看用户的实际提问倾向再判断。
